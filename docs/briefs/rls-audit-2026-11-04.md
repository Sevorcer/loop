## 1. Executive summary (plain language)

**Overall, the database is locked down well.** All 58 tables have row-level security turned on. Row-level security is the rule layer that decides who can see or change each row. Almost every rule checks two things: which company you belong to and what your job role is. Money tables (invoices, payments, estimates, prices) are invisible to anyone who isn't signed in. All three file buckets are private. The earlier "make yourself owner" hole is closed: a signed-in person can change only their own display name, and a guard in the database blocks role and company changes.

**What needs fixing, most important first:**

1. **High: any signed-in employee, even a tech, can create a public builder-portal link for any job.** The app's button only lets office staff do this. The database rule behind it is looser: it lets anyone in the company add, read, change or delete share links. A tech who calls the database directly, without using the Loop screens, could make a working public link to a job they aren't assigned to. Today there are 0 share links, so nothing has leaked. This should be tightened before the portal share button goes live.
2. **High (Known item #1, confirmed): the builder request form table accepts rows from anyone on the internet** (`service_insert_portal_submissions`). Confirmed: the real submit page writes through the server's admin key, which skips these rules entirely, so this rule isn't needed. One detail lowers the urgency a little: an outsider would also need the internal ID of a real share link, and there are 0 links today. It's being fixed separately. The same table has a second problem: any employee, including a tech, can read, edit or delete every builder request.
3. **Medium: the "not signed in" role still holds read/write permission on 47 of 58 tables.** Only the row rules are stopping it, and they currently do. This is like a locked inner door with the outer door left open. Closing the outer door is a safe, standard hardening step, because the app never uses that role to read tables.
4. **Medium: techs can see more than "only their own jobs".** At the database level, a tech can read every customer contact (1,834), every installed system (2,778), and the whole dispatch board including customer names (3,598 rows). Some of this is on purpose. The app code says "all internal roles, including tech, can read contacts". This is a business decision for Collin, not a bug. A draft is included in case you want it tighter.
5. **Medium (mostly speed and tidiness): 243 "multiple permissive policies" warnings.** These come from 178 rules written as "applies to everyone" instead of "applies to signed-in users". Each one then gets checked for 6 database roles. Re-pointing them at signed-in users only is mechanical, and it drops the warnings to about 43.
6. **Low items:** feedback screenshot uploads are open to any signed-in account. One unused leftover function would trust a user-editable signup field if it were ever re-attached. One rule that looks like "no deleting" actually does nothing. There are a few advisor housekeeping notes. Leaked-password protection is off, which is a toggle in the Supabase dashboard.

**Good news to keep:** RLS is on for all 58 tables. There are no views that skip the rules. Role escalation is blocked. Finance tables have no "not signed in" access. Buckets are private. Job-file storage rules piggyback on the jobs rules, so techs only reach files on their assigned jobs. Every privileged helper function pins its search path. The Service Fusion import function can't be called by app users.

## 2. What the app legitimately needs (code cross-check)

From the code at `0e96509`:

| Client | Where | What it touches | Notes |
|---|---|---|---|
| **Browser client** (`src/lib/supabase/client.ts`, anon key + user JWT) | `services/authClient.ts`, `services/profileDirectory.ts` | `auth.*` (sign-in, session, password) and **`user_profiles` SELECT only** (`loadOwnProfile`, `lookupProfileName`, `loadProfileNames`) | No other table, storage, or RPC calls from the browser. |
| **Server session client** (`src/lib/supabase/server.ts`, anon key + the caller's cookie JWT) | `repositories/supabaseContext.ts` → nearly every `/api/*` route; `repositories/storage.ts` (upload, sign, remove) | All business tables and `storage.objects`, **as the signed-in user**, so RLS is the real enforcement layer | With no signed-in user it throws `SUPABASE_SESSION_REQUIRED` (prod). It never queries as `anon`. |
| **Admin client** (`src/lib/supabase/admin.ts`, service role, server-only) | `api/portal/[token]/submit`, `services/jobShareLinks.resolveShareToken`, `services/portalJobData`, `services/settingsUsers`, `repositories/organizations`, `repositories/dbHealth`, reset-password route | Bypasses RLS | All public, unauthenticated portal reads and writes go through here, which is the intended design. |

**What follows from this:**

- The `anon` role never needs any table privilege in `public`, so revoking it is safe (Draft D3).
- Changing `TO public` to `TO authenticated` is safe for every policy, because every legitimate caller is either `authenticated` (browser and session client) or `service_role` (admin, which bypasses RLS) (Draft D4).
- Known item #1 is confirmed. `POST /api/portal/[token]/submit` (lines ~86–112) does `getSupabaseAdminClient()` → `.from("portal_submissions").insert(...)`. The `service_insert_portal_submissions` policy is not needed by the app.

## 3. Findings, ranked

### HIGH-1: `job_share_links`: any org member can mint, read, revoke or delete public portal links

**Evidence**
- Policy `org_isolation_job_share_links`: `PERMISSIVE`, roles `{public}`, cmd `ALL`, `USING (org_id = (SELECT user_profiles.org_id FROM user_profiles WHERE user_profiles.id = auth.uid()))`, **no WITH CHECK** (so USING doubles as the insert check), **no role check**.
- Grants: `authenticated` has SELECT/INSERT/UPDATE/DELETE. FORCE RLS is off.
- App: `POST /api/jobs/[id]/share-link` restricts creation to `OFFICE_PLUS = owner, manager, dispatch, office`. The database doesn't, so a tech's JWT can `insert` directly through PostgREST.
- How a link is used: `resolveShareToken()` (admin client) accepts **any** non-revoked row whose `token_hash = sha256(token)`. A tech could pick a random 64-hex token, insert its hash for any `job_id` in the org (the FK only needs the job to exist), and open `/gc-portal/<token>`. That exposes the job's portal view publicly, including jobs they aren't assigned to.
- Current exposure: **0 rows** in `job_share_links`, so nothing has leaked. Severity rises when the portal share button ships.
- Also flagged by the performance advisor (`auth_rls_initplan`: bare `auth.uid()`), and FK indexes are missing on `job_id` and `created_by`.

**Fix:** Draft D2. Replace it with office+ role-scoped, org-keyed policies `TO authenticated`, with insert requiring `created_by = auth.uid()` and the job in the same org. Add no DELETE policy, because the app revokes links by setting `revoked_at`.

### HIGH-2: Known item #1: `portal_submissions` insert open to PUBLIC (confirmed), plus no role scoping

**Evidence**
- `service_insert_portal_submissions`: `PERMISSIVE`, roles `{public}`, cmd `INSERT`, `WITH CHECK (true)`. **Confirmed as described.**
- `anon` has INSERT privilege, so anyone with the public anon key can `POST /rest/v1/portal_submissions`.
- Mitigating factor: `share_link_id`, `job_id` and `org_id` are NOT NULL with foreign keys, so a junk row needs a real share-link UUID. There are 0 links today. Link IDs do appear in staff API responses, though, so this is latent rather than harmless.
- Second issue: `org_isolation_portal_submissions` is `ALL` with no role check and no WITH CHECK. Any employee, including a tech, can SELECT/UPDATE/DELETE every builder submission in the org (names, companies, contact info, messages) and INSERT new ones. The app's PATCH route (guard `jobs.update`, which includes tech) doesn't check that a tech is assigned to the job.
- The app is confirmed to insert via the admin client only, so no authenticated INSERT or DELETE policy is needed.

**Fix:** being handled separately for the insert policy. Draft D1 also includes the companion role scoping for the `ALL` policy. Treat that part as optional, and coordinate so it doesn't collide with Zoinks' migration.

### MEDIUM-1: `anon` holds full table grants on 47 / 58 public tables; helper functions executable by anon

**Evidence**
- `has_table_privilege('anon', …)` is true for SELECT/INSERT/UPDATE/DELETE on every public table **except** `calendar_saved_group_members`, `calendar_saved_groups`, `customer_contacts`, `estimate_line_items`, `estimates`, `invoices`, `job_financials`, `job_financials_history`, `job_line_items`, `payments`, `user_profiles`. Those 11 were already hardened.
- Today every policy reachable by anon evaluates to false or NULL, because `current_app_role()` and `current_org_id()` return NULL when there is no `auth.uid()`. The only exception is HIGH-2. So nothing is readable right now. One careless future policy (for example `USING (true)` without `TO`) would immediately expose a table to the internet, as HIGH-2 shows.
- Security advisor `anon_security_definer_function_executable`: `public.current_app_role()` and `public.current_org_id()` are SECURITY DEFINER and callable by anon via `/rest/v1/rpc/…`. For anon they return NULL, so the impact is low. They should still not be exposed.
- `pg_graphql` is installed (`graphql` and `graphql_public` schemas), so the same grants also govern the GraphQL endpoint.

**Fix:** Draft D3: revoke anon on tables and sequences, change the default privileges, and revoke anon/PUBLIC execute on the two helpers.

### MEDIUM-2: Permissive-policy pileup: 243 advisor warnings, 182 policies `TO public`

**Evidence**
- 192 public-schema policies: **182 are `TO public`** and 10 are `TO authenticated`.
- The `multiple_permissive_policies` advisor reports **243 warnings across 29 tables**. That is 43 distinct (table, action) pairs × 6 roles (`anon`, `authenticated`, `authenticator`, `cli_login_postgres`, `dashboard_user`, `supabase_privileged_role`). The one exception is `feedback_reports`, whose policies are already `TO authenticated` (3 warnings).
- Security impact: low today, because every policy is role- and org-gated. `TO public` does make every rule apply to anon too, which is how HIGH-2 happened. The performance impact is that Postgres evaluates every permissive policy for an action and ORs the results.
- The full grouping is in section 5.

**Fix:** Draft D4 (mechanical): `ALTER POLICY … TO authenticated` for the 178 remaining `TO public` policies. That takes warnings from about 243 to about 43. Merging overlapping pairs (for example "org read" + "org write" `ALL`) would clear the rest. That is a bigger refactor and not drafted here.

### MEDIUM-3: Role scoping: techs can read org-wide data beyond their assigned jobs

These policies are company-keyed (no cross-company leak), but they let `tech` read **every** row in the org:

### Verified OK (no action)

- **RLS enabled on all 58 public tables.** There are no views or materialized views in `public`, so nothing bypasses RLS that way.
- **Role escalation via `user_profiles` is closed.** `authenticated` column grants are SELECT on all columns and UPDATE on **`full_name, updated_at` only**. There is no INSERT or DELETE grant. The `guard_user_profile_write` trigger also blocks changing id or company, changing your own role, non-owner/manager role changes, and non-owners granting or removing `owner`. Current roles: owner 1, manager 2, office 1, dispatch 1, tech 8. There are 0 profiles with a NULL org, and 13 auth users, all with a profile.
- **Role and org helpers read from `user_profiles`**, not from JWT `user_metadata`. They aren't spoofable.
- **Storage:** all 3 buckets are private (`feedback-screenshots` 2 objects, `job-files` 1,245, `job-signatures` 4). The `job-files` and `job-signatures` SELECT/INSERT policies check `EXISTS (SELECT 1 FROM jobs …)`, and that subquery runs under the caller's own `jobs` RLS. So techs only reach files on assigned jobs, and nobody reaches another company's job files.
- **SECURITY DEFINER functions:** every one sets `search_path`. The `dbhc_*` functions and `handle_new_user` are not executable by anon or authenticated. `sf_import_apply_batch` (SECURITY INVOKER) is not executable by anon or authenticated, and also self-rejects those JWT roles. `private.*` helpers live in a non-exposed schema.
- **Finance tables** (`invoices`, `payments`, `estimates`, `estimate_line_items`, `job_line_items`, `job_financials`, `job_financials_history`) have no anon grants and money-role-only read. Techs see only assigned jobs on line items and financials.
- **Tech write guards** exist as triggers on `jobs`, `dispatch_plans`, `job_tasks`, `calendar_tasks` and `installed_systems`. Same-company FK triggers exist on the money and imported tables.

### D1: `portal_submissions`: drop the PUBLIC insert hole and add role scoping

```sql
-- DRAFT D1 — NOT APPLIED
begin;

-- Known item #1 (being fixed separately; keep only one copy of this line).
-- App inserts via the service-role admin client, which bypasses RLS.
drop policy if exists service_insert_portal_submissions on public.portal_submissions;

-- Replace the role-less ALL policy.
drop policy if exists org_isolation_portal_submissions on public.portal_submissions;

create policy "portal_submissions: staff read"
  on public.portal_submissions for select to authenticated
  using (
    org_id = (select public.current_org_id())
    and (
      (select public.current_app_role()) = any (array['owner','manager','dispatch','office','sales'])
      or ((select public.current_app_role()) = 'tech' and private.caller_is_assigned_to_job(job_id))
    )
  );

create policy "portal_submissions: office reviews"
  on public.portal_submissions for update to authenticated
  using (
    org_id = (select public.current_org_id())
    and (select public.current_app_role()) = any (array['owner','manager','dispatch','office'])
  )
  with check (
    org_id = (select public.current_org_id())
    and (select public.current_app_role()) = any (array['owner','manager','dispatch','office'])
  );

-- No INSERT / DELETE policy for authenticated: inserts come only from the admin client.
alter table public.portal_submissions force row level security;
create index if not exists portal_submissions_share_link_id_idx on public.portal_submissions (share_link_id);

commit;
```

App impact: a tech hitting PATCH `/api/jobs/[id]/portal-submissions` would update 0 rows (techs shouldn't triage builder requests). Consider also tightening that route's guard to office+.

### D2: `job_share_links`: office+ only, org-keyed, no role-less ALL

```sql
-- DRAFT D2 — NOT APPLIED
begin;

drop policy if exists org_isolation_job_share_links on public.job_share_links;

create policy "job_share_links: office read"
  on public.job_share_links for select to authenticated
  using (
    org_id = (select public.current_org_id())
    and (select public.current_app_role()) = any (array['owner','manager','dispatch','office'])
  );

create policy "job_share_links: office create"
  on public.job_share_links for insert to authenticated
  with check (
    org_id = (select public.current_org_id())
    and (select public.current_app_role()) = any (array['owner','manager','dispatch','office'])
    and created_by = (select auth.uid())
    and exists (
      select 1 from public.jobs j
      where j.id = job_share_links.job_id and j.org_id = job_share_links.org_id
    )
  );

create policy "job_share_links: office revoke"
  on public.job_share_links for update to authenticated
  using (
    org_id = (select public.current_org_id())
    and (select public.current_app_role()) = any (array['owner','manager','dispatch','office'])
  )
  with check (
    org_id = (select public.current_org_id())
    and (select public.current_app_role()) = any (array['owner','manager','dispatch','office'])
  );

-- No DELETE policy: the app revokes by setting revoked_at. Public token lookups use the admin client.
alter table public.job_share_links force row level security;
create index if not exists job_share_links_job_id_idx on public.job_share_links (job_id);
create index if not exists job_share_links_created_by_idx on public.job_share_links (created_by);

commit;
```

App impact: `GET /api/jobs/[id]/share-link` (guard `jobs.select`, includes tech and sales) will return "no active link" for tech and sales, which matches the route's office+ create/revoke rule. `POST` and `DELETE` are unchanged for office+.

### D3: Remove `anon` privileges (defense in depth)

```sql
-- DRAFT D3 — NOT APPLIED
-- Safe because the app never queries tables as anon: browser + server session
-- clients always carry a user JWT (authenticated); public portal uses service_role.
begin;

revoke all on all tables    in schema public from anon;
revoke all on all sequences in schema public from anon;
revoke execute on function public.current_app_role() from public, anon;
revoke execute on function public.current_org_id()   from public, anon;
grant  execute on function public.current_app_role() to authenticated, service_role;
grant  execute on function public.current_org_id()   to authenticated, service_role;

-- Stop future tables/sequences from auto-granting anon (objects created by postgres).
alter default privileges for role postgres in schema public revoke all on tables    from anon;
alter default privileges for role postgres in schema public revoke all on sequences from anon;

commit;
```

Note: after this, anon REST and GraphQL calls on public tables return `42501 permission denied` instead of empty results. The sign-in page and the public `/gc-portal` page aren't affected, because they use Auth and the admin client.
